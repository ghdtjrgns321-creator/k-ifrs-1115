# K-IFRS 1115호 특화 RAG 챗봇

> **라이브 데모 배포 → http://134.185.104.224:8501/** (Oracle Cloud 배포, Streamlit)

## 개요

K-IFRS 제1115호(수익인식) **기준서 원문 기반** 도메인 특화 RAG 챗봇. 검색 진입부에서 벡터 유사도를 걷어내고, 기준서가 이미 갖고 있는 참조 구조를 따라가도록 바꿨다.

### 왜 1115호인가

수익인식은 금액 계산보다 계약 맥락에 따른 정성적 판단이 결론을 가른다. 같은 거래라도 본인이냐 대리인이냐, 통제가 언제 이전되느냐에 따라 회계처리가 갈린다.

그래서 회계기준원 질의회신과 감리지적사례가 타 기준서 대비 가장 많이 쌓여 있다. 실무자가 가장 자주 막히는 지점이라는 뜻이다.

동시에 5단계 수익인식 모형·본인 대 대리인·재매입약정처럼 조건부 분기가 원문에 서술돼 있어, 판단 절차를 코드 구조로 옮기기에 적합하다.

### 무엇이 문제였나

**범용 LLM** — 근거 문단을 추적할 수 없고, 기준서에 없는 판단을 지어낸다. 회계에서 최악의 오류는 모른다고 답하는 것이 아니라 틀린 것을 확신에 찬 어조로 답하는 것이다(2종 오류 · §1).

**통상적 RAG** — 이 프로젝트도 처음에는 벡터 임베딩 + 카테고리 가중치 + Cohere 리랭커로 만들었고, 실패했다.

가장 분명한 장면은 리랭커였다. 직접 매핑해 둔 관련 문서 **105건 중 103건**을 임계값 미만으로 판정해 탈락시켰다.

유사도 자체도 낮았고 신호끼리 충돌해, 같은 질문에도 라우팅 결과가 달라졌다. 전환 경위는 §9에 단계별로 적었다.

### 무엇을 했나

기준서에는 이미 명시적 참조 구조가 있다 — 목차 위계, "제N문단 참조", 본문과 부록B의 대응, 사례가 인용한 문단. **비슷한 것을 추측하는 대신 연결된 것을 따라가도록** 검색 진입부를 바꿨다.

1. Analyze  : 용어사전으로 개념 진입 (임베딩 없이 글자 매칭)
2. Retrieve : 지식그래프 순회 — 개념 → 관할 문단 → 참조 이웃 → 사례
3. Generate : 기준서 문단으로 만든 판단트리 주입 + 듀얼 LLM(회계추론 or 산술) 라우팅
4. Format   : PydanticAI 구조화 출력 — 인용이 없으면 답도 없음

```
   사용자 질문
       │
       ▼
 ┌──────────────────────── FastAPI  /chat  (SSE 스트리밍) ────────────────────────┐
                                                                   ㅤ  ㅤ ㅤ     
    analyze  ───▶   retrieve   ───▶   generate   ───▶   format                
    용어사전        지식그래프 탐색    판단트리 주입         PydanticAI   ㅤㅤ     
    개념진입 (LLM)  개념→문단→사례     듀얼 LLM 라우팅      구조화된 답변ㅤㅤㅤㅤㅤ
```

### 무엇이 확인됐나

실제 질의회신 92건을 **홀드아웃**(정답을 감춘 채 시험만 보게 한 세트)으로 두고 쟀다.

| 무엇을 쟀나                                  | 값                           |
| -------------------------------------------- | ---------------------------- |
| **확정 결론 재현**                           | **80/92**                    |
| 평가셋 자가순환 유입 (자기 답을 자기가 인용) | 0/92                         |
| 그래프 완전성 (**census** — 전수 대조 검사)  | 누락 0 · 도달불가 0 · 고아 0 |
| 실행 에러                                    | 0/92                         |

재현하지 못한 12건은 유형별로 §7에 그대로 적었다.

### 어디까지이고, 어디부터 아닌가

- **1115호 한 기준서 안에서만** 동작한다. 정답이 타 기준서에 있으면 회수하지 못한다
- **완전한 GraphRAG는 아니다** — 엔티티 추출도 커뮤니티 요약도 없다 (§4 범위 한계)
- **검색 경로는 결정적이지만 답변 문구가 고정은 아니다** — 진입 판단(analyze)과 최종 생성이 LLM이라, 같은 질문에도 회수 문단과 표현이 달라질 수 있다 (§10 한계 4)

## 1. 문제 인식 

### 범용 LLM 한계와 본 시스템의 해결 방안

| 구분      | 범용 LLM                              | 본 시스템                                                                                                      |
| --------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 근거 추적 | 블랙박스 형태(조문 추적 어려움)       | 지식 그래프 기반 개념→문단→사례 추적 근거 제시                                                                 |
| 재현성    | 동일한 질문에 매번 다른 답            | 그래프 순회가 결정적 — 같은 개념으로 진입하면 같은 문단이 나옴 (진입 판단·최종 생성은 LLM이라 변동 여지 · §10) |
| 판단 출처 | 기준서에 없는 판단을 지어낼 위험      | 사전 정의된 판단트리로 추론 절차 통제                                                                          |
| 환각 위험 | 그럴듯한 오답 생성(**2종 오류 위험**) | 근거 부족이라고 명확히 응답                                                                                    |

### 회계감사의 핵심 리스크: 2종 오류

잘못된 정보를 사실처럼 제시하는 것이 훨씬 큰 비용 초래

| 오류     | 정의                                            | 위험도                          |
| -------- | ----------------------------------------------- | ------------------------------- |
| 1종 오류 | 근거가 존재함에도 찾지 못해 "모른다"고 응답     | 낮음 — 추가 검색으로 보완가능   |
| 2종 오류 | 근거가 없거나 틀린 내용을 확신에 찬 어조로 답변 | **치명적** — 큰 비용으로 이어짐 |

본 파이프라인은 2종 오류의 최소화에 초점을 맞추고 있음
- 통제된 답변: 근거 없는 확정적 답변 생성을 구조적으로 차단
- 엄격한 판단: 기준서에 명시된 확실한 조건에서만 결론을 도출
- 유보적 접근: 내용이 모호하거나 교차 검증이 필요한 경우 조문만 제시하고 최종 판단을 유보

## 2. 실증 예시

**질문**(QNA-2017-I-KAQ015-Q1) : 아파트 분양계약으로 고객이 1차 중도금 납부 전엔 해제 가능(위약금 분양대금의 10%), 이후엔 해제불가. 이때 회사가 수행완료분에 대한 집행 가능한 지급청구권을 가져 진행기준을 적용할 수 있는가

  1. analyze (gpt-4.1-mini)
  - 판별1 : 이 질문이 수익인식 기준(1115호) 안의 것인지(→ 맞음)
  - 판별2 : 금액을 계산? 회계추론? (→ 회계추론)
  - 판별3 : 질문에 걸린 용어판별 → 지식그래프의 개념 6개(계약 식별·대체용도 없는 자산·지급청구권·변동대가 등)로 연결
  2. retrieve 
  - 개념 6개 각각의 기준서 문단 → 참조하는 이웃 문단 → 관련 사례를 그래프를 따라 retrieve(총 문서 159개)
  3. generate 
  - 기준서를 따라 미리 만들어둔 의사결정나무(문단 35·37·B9·B11)에 주입되어 답변이 분기됨
    - Case 1 — 중도금 전 공정진행률이 10% 미만이면 → 지급청구권을 인정, 진행기준(문단 35·B9)
    - Case 2 — 공정진행률이 10%를 넘는 시점이 있으면 → 그 시점엔 권리가 약해 인도기준(문단 37·B12)
  4. format
  - 인용 없으면 답 없음 
  - 분기 라벨을 필드로 강제 : 답을 산문으로 뽑지 않고 구조적으로 강제
  - 환각 필터 : 실제 컨텍스트에 있던 키만 통과, 없는 사례번호는 걸러짐

## 3. 기술 설명 ① 진입점 — 용어사전 

```
 ━━━ [1] analyze : LLM(gpt-4.1-mini) 1회 호출 — 질문 + 멀티턴 구성(최근3턴) ━━━


    ◆ 패스스루 축   →  뒤 노드(generate/format)로 전달
      needs_calculation  ┳ true  = 계산      → gpt-4.1-mini
                         ┗ false = 회계추론  → Gemini Flash
      is_situation       계약당사자, 거래조건, 계약구조 중 2개 이상 존재 → generate clarify(꼬리질문) 분기
                         1개인 경우 → 단순 기준서 찾아주기
      complexity         답이 하나로 정해지는지?  →  simple / complex   → Gemini thinking_level (low / medium)
      confusion_point    사용자 오해 원인(LLM추론)    → clarify 프롬프트 주입(오해 교정)
      provided_info      질문에서 이미 명시한 판단요소  → clarify 재질문 방지

    ◆ 개념 진입 축   →  analyze[2]~[5]로 전달
      topic_hints       최대 3개 · 거래 실질상 쟁점이면 지목(고정 35토픽 중 개념 매핑 보유 33개가 실효 진입)
      standalone_query  멀티턴 재구성 — 회사명·금액 제거(추상화) → 1115호 공식용어로 번역(정규화)
                    
    ◆ 게이트
      routing (1115호 IN / OUT)    
          │ 
          ├── routing = OUT ──▶ 범위 밖 거절 · 파이프라인 종료
          ▼   routing = IN , scope guard : routing=IN 이어도 타기준서 전용어만 존재하고, 1115호 앵커(수행의무·거래가격…)가 없으면 다시 OUT
  ━━━ 개념 진입 ━━━

    [2] topic_hints → 개념   (_resolve_topic_hint)
          topic_map - "수행의무 식별" → "수행의무" 부분매칭 흡수
          → via_topic 확정
          ※ via_topic = "결정적 신호" : retrieve의 케이스·IE, generate의 판단트리 선택 한정
          │
          ▼
    [3] subtree 확장   (_adaptive_subtree)
          via_topic 개념의 형제·하위 개념을 뒤에 붙임 (2순위 · gap 보강)
          부모 하위트리(자기 제외) ≤ 8(subtree_expand_max) → 형제 포함 / 그보다 크면 → 자기 하위만(문단 폭발억제)
          │
          ▼
    [4] 용어사전 조회   (resolve_terms)
          입력 = standalone_query (없으면 사용자 원문)
          aliases 용어(파일 423 · 매칭 인덱스 400) 중 입력에 substring으로 걸린 것 → 그 용어의 개념·사례 회수 (LLM 무관)
          │
          ▼
    [5] concept_ids 확정
          1순위(via_topic) → 2순위(subtree) → 3순위(용어사전) 순서로 병합 · 중복 제거
          ※ 개념 순서 = 문단 우선순위 (traverse가 개념 순서대로 문단을 채움 → 질문 주제 문단이 앞자리)
          → retrieve 노드로 넘김 (via_topic · entry_cases 동반)
```
### 용어 사전 구축 방식

1. 초안 생성 (GPT o4-mini)
- 자주 쓰이는 말(판매장려금·리베이트·풋옵션…)을 GPT(o4-mini)로 1115호 공식용어 2~4개에 매핑
- 수익인식,거래가격와 같은 범용어에는 매핑되지 않도록 규칙 → 실무어 사전 초안 288개

2. 지식그래프 생성 후 - 용어사전 조립
- ① 진입 어휘 확정
  - 초안 288개 + 사례 제목 123개(질의회신·감리지적사례의 제목) + 부록A 공식 정의 9개
  - 아이템,항공과 같은 단독으로 진입하지 못할 단어들은 제외 
- ② 개념에 연결
  - 각 단어를 그래프 개념에 글자 비교로 자동 연결. (오타·조사 차이 허용 → 대리인 = 본인 대 대리인의 고려사항)
  - 애매한 단어 78개 AI가 → 근거 문단을 보고 판단(그대로 채택 41·손봄 34·사용자 직접 결정3(시상품·아이템·항공))
- ③ 사각지대 보완
  - 단어들이 실제 개념까지 연결되는지 전수 점검 
  - 연결이 부실한 항목 확인 및 본문을 근거로 보완

## 4. 기술 설명 ② RAG — 지식그래프

기준서의 명시적 위계 관계를 노드·간선으로 옮긴 지식그래프

```
                     거래가격을 산정함        ← ① 위 : 부모 개념
                           │  (부모–자식)
                           ▼
                     
                        변동대가     ─── ② 옆 : 형제 개념 3개
                           ┬              (유의적 금융요소 · 비현금대가 · 고객에 지급할 대가)
          ┌────────────────┼────────────────┬────────────────┐
          ▼                ▼                ▼                ▼
     ③ 아래: 자식      ④ 자기 원문        ⑤ 사례           ⑥ 배경(BC)
     환불부채          관할 문단          이 개념을         "왜 변동대가를
     ·제약·재검토      50·51·52·53·54     다룬 QNA·지적사례   제약하나"
                          │
                          └─ ⑦ 문단끼리 "○문단 참조" (상호참조)

변동대가 하나가 이렇게 8~10개와 이어지고, 개념 80개가 다 이렇게 얽히면
→ 3D 뷰어에 그려지는 선 2,694개 (용어→개념 755선 포함 · 아래 표와는 집계 단위가 다름)
```
1. 개념 위계는 AI 판단 없이 기준서 본문 구조로만 구성됨
  - 개념 노드와 그 상하관계(부모–자식)는 기준서의 목차·소제목 위계 "어느 개념이
  - 개념 80개 · 계층 간선 79개 · 관할 문단 250개 배정
2. QNA·감리 사례는 문단으로 1차 연결 → 제목으로 보강
  - 문단 인용이 약하거나 없는 사례→ 제목 자체를 용어사전 별칭으로 등재(123건)해 "제목 → 개념" 진입
  - 문단 인용이 0인 6건은 질의 원문 근거로 개념에 직접 연결

### 관계 종류

## 6. 기술 설명 ④ PydanticAI

```python
# 레이어 2 — 출력 스키마 고정
class ClarifyOutput(BaseModel):
    selected_branches: list[str]   = Field(..., description="고른 결론 분기")       # 어느 Case로 결론?
    answer: str                    = Field(..., description="답변 본문(마크다운)")
    cited_paragraphs: list[str]    = Field(..., description="인용 문단 — 비면 거부")  # 근거 필수
    cited_cases: list[str]         = Field(default_factory=list)  # 질의회신·감리 ID
    cited_ie: list[str]            = Field(default_factory=list)  # 적용사례 번호
    follow_up_questions: list[str] = Field(default_factory=list)
    is_conclusion: bool            = Field(default=True)

# 스키마를 에이전트에 물림 → LLM이 이 JSON을 못 채우면 PydanticAI가 자동 재프롬프트
clarify_agent = Agent(gemini_flash, output_type=ClarifyOutput, retries=2, ...)

# 레이어 3·4 — 스키마 통과 뒤 '한 번 더' 검사. 실패하면 ModelRetry로 재생성
@clarify_agent.output_validator
async def _validate(ctx, result: ClarifyOutput) -> ClarifyOutput:
    errors = []
    if not result.cited_paragraphs:              # 레이어 3: 인용 비면 → 다시
        errors.append("근거 문단을 반드시 포함하세요.")
    if not result.selected_branches:
        errors.append("고른 결론 분기를 포함하세요.")
    # 레이어 4: 핵심 사실 미확인인데 확정(분기 1개=TYPE2)이면 → 조건부로 강등 요구
    if len(result.selected_branches) == 1 and _핵심사실_미확인(ctx):
        errors.append("아직 확인 안 된 요소가 있습니다. 조건부(TYPE1)로 바꾸세요.")
    if errors:
        raise ModelRetry("\n".join(errors))      # ← 이 메시지로 LLM에 자동 재요청
    return result
```

## 8. 기여 — AI를 어디에 쓰지 않았는가

만든 것은 챗봇이지만, 남은 것은 **회계 도메인 RAG에서 AI를 어디까지 걷어낼 수 있는가**를 한 번 끝까지 밀어본 기록이다.

### 단계별로 무엇을 걷어냈나

| 단계        | 통상적 RAG                 | 이 프로젝트                       | 걷어낸 자리에 넣은 것     |
| ----------- | -------------------------- | --------------------------------- | ------------------------- |
| 검색 진입   | 쿼리 임베딩 → 유사도 top-k | 용어사전 글자 매칭 → 개념 노드    | 등재 용어 423             |
| 순위        | 리랭커 + 카테고리 가중치   | 그래프 간선 1홉 순회              | 관할 250 · 상호참조 264   |
| 그래프 뼈대 | LLM이 엔티티·관계를 추출   | 기준서 목차·문단번호 구조         | 개념 80 · 계층 간선 79    |
| 판단 분기   | LLM이 매번 문단에서 조립   | 원문이 서술한 분기를 그대로       | 판단트리 (AI 창작 분기 0) |
| 남긴 AI     | —                          | 진입 판단 · 별칭 확장 · 최종 생성 | —                         |

정확히는 **dense 임베딩만 뺀 것**이다. 용어사전 글자 매칭도 lexical 검색 계열이므로, 통상 하이브리드 3축(dense · lexical · graph) 중 dense를 빼고 나머지 둘로 간 구성에 가깝다.

### 걷어내서 얻은 것

- **근거 역추적** — 어떤 용어로 들어가 어떤 개념을 거쳐 어떤 문단에 닿았는지가 답변과 함께 나온다
- **그래프 자체의 환각 배제** — 뼈대가 LLM 생성물이 아니라서 근거 경로를 지어낼 여지가 없다
- **오류의 방향 전환** — 못 찾으면 조용히 섞는 대신 범위 밖으로 거절한다 (2종 → 1종)
- **측정된 것** — 홀드아웃 92건 중 결론 재현 80건. 오염판(78건) 대비 무영향이라, 이 성적이 평가셋 누출 덕이 아님을 확인했다

### 걷어내서 잃은 것

- **어휘 불일치** — 등재되지 않은 말로 물으면 진입 자체가 실패한다. 임베딩이 존재하는 이유가 이것이고, 미재현 사례 중 개별소비세(`KQA007`)·환불부채(`38673`)가 그 유형이다
- **확장 비용** — 개념 80 · 용어 423 · 판단트리가 전부 수작업 큐레이션이다 (§10 한계 1)
- **단일 기준서** — 다기준서로 넓히면 용어 충돌과 간선 폭증이 생기며, 그 조건에서도 결정적 진입이 유효한지는 검증하지 않았다

### 같은 방향의 흐름

이 선택이 취향이 아니라 도메인 특성에서 나왔다는 근거로, 같은 문제의식이 2025~2026년 법령·규정 도메인에서 이름을 얻고 있다.

- **structure-aware · deterministic retrieval** — 법령에서는 유효 시점·상위 구조·개정 이력이 관련성을 좌우한다. 더 나은 임베딩이 아니라 구조와 출처를 일급 제약으로 노출하자는 쪽
- **vectorless RAG** — 청킹이 문서의 논리적 위계를 파괴한다는 문제 제기. 숫자 한 자리나 괄호 참조가 의미를 바꾸는 도메인에서 특히 치명적이다

감사 전용 어시스턴트를 만드는 회사들이 내세우는 문구도 대체로 "출처 자료 참조 제공"과 "환각 리스크 관리"다. 이 프로젝트가 던진 질문도 다르지 않다.

갈린 것은 그것을 **운영 정책으로 약속할 것인가, 파이프라인 구조로 강제할 것인가**다.

성능 비교는 하지 않는다. 상용 도구는 내부 전용이라 측정할 수 없고, 이 프로젝트도 인용된 문단 번호의 진위까지는 검증하지 못한다.

### 다음 단계

- **그래프 랭킹** — 지금 순회는 문단·사례를 삽입 순서대로 쌓아 LLM에 넘긴다. 진입 개념을 시드로 삼는 확산 랭킹(Personalized PageRank 계열)을 얹으면 난수도 임베딩도 없이 후보를 좁힐 수 있다. §10 한계 6이 겨냥하는 지점이다
- **임베딩 폴백** — 글자 매칭이 0건일 때만 유사도 진입을 태우면 결정적 경로를 유지한 채 어휘 불일치만 보완할 수 있다. 다만 그 진입은 "유사도로 들어왔다"고 표시되어야 한다

## 9. 핵심 의사결정 — 검색 진입부를 왜 갈아엎었나

```
  ━━━ 진입부 3차 전환 · 각 단계는 앞 단계의 결핍 때문에 등장했다 ━━━

    [1] 벡터 임베딩 top-k
          ┗ 결핍 : 일상어 질의와 기준서 원문의 유사도가 낮아 순위가 흔들림
          │
          ▼
    [2] + 카테고리 가중치      본문·QNA·지적사례에 점수를 부여
          ┗ 결핍 : 점수의 근거가 사용자 판단뿐 — 논리 없는 확률값이 최상단을 지배
          │
          ▼
    [3] + Cohere 리랭커        3중 신호(키워드·리랭커·임베딩)로 재정렬
          ┗ 결핍 : 관련 문서를 임계값 미만으로 대량 탈락 · 신호끼리 충돌해 라우팅이 요동
          │
          ▼
    [4] 지식그래프 순회   ◀ 현재
          기준서가 이미 그어 놓은 연결(목차 위계 · 문단 참조 · 부록B 대응)을 따라감
          ┗ 남은 결핍 : 어휘 불일치 · 후보를 좁히는 축 부재 (§10 한계 6)
```

초기에는 벡터 임베딩, 가중치 산정, Cohere 리랭커를 결합한 전형적인 RAG 방식을 적용했으나 검색 순위를 결정하는 신호에 명확한 기준이 부재했다.

**가중치 산정의 근거 부재** 
- 근거 없이 사용자의 판단으로만 본문, QNA, 지적사례등에 점수를 부여했음
- 논리적이지 않은 확률값이 검색 결과의 최상단을 지배함

**임베딩 유사도의 높은 변동성** 
- 사용자의 일상어 질의와 기준서 원문 간 유사도 절대값은 0.29~0.47 수준으로 낮았음
- 키워드·LLM(리랭커)·임베딩의 3중 신호가 서로 충돌하면서 동일한 질문에도 라우팅 결과가 달라지는 재현성 없는 검색이 발생
- Cohere 리랭커가 직접 맵핑한 관련 문서 105건 중 103건을 임계값(0.05) 미만으로 판정하여 누락시키는 등의 문제 발생

**결론**
- 이미 회계 기준서는 명시적인 상호 참조 구조(5단계 모형·문단 간 참조·본문과 부록B의 연결)를 가짐
- 단순 유사도와 근거 없는 가중치를 사용한 것이 문제
- 기존의 확률 기반 검색 진입부를 개편하고 비슷한 것을 추측하는 대신 연결된 것을 추출하는 지식 그래프로 전환
- AI와 사람의 개입을 최소화

| 임베딩(유사도)                      | 온톨로지(지식그래프)                     |
| ----------------------------------- | ---------------------------------------- |
| 비슷한 것 위주 유사도 상위 N개 추출 | 기준서 상 명시적 관계 존재               |
| 확률적이고 설명 불가                | 결정적이고 근거를 경로로 제시            |
| 내용 오염으로 인한 환각위험         | 판단 불가 시 검색 실패로 안전하게 드러남 |

### 전환의 근거는 점수가 아니라 결함이었다

① 정당화할 수 없는 가중치 ② 관련 문서 105건 중 103건을 탈락시킨 리랭커 — 둘 다 점수를 재기 전에 이미 고쳐야 할 것이었다.

세 번째였던 재현성은 **해결이 아니라 축소**다. 검색 구간에서 결과를 바꿀 수 있는 단계가 7개에서 0개로 줄었다.

| 검색 구간 (진입 판단 이후 ~ 생성 이전) | 구 시스템 | 현재 |
| -------------------------------------- | :-------: | :--: |
| LLM 호출 (HyDE 가상문서 생성)          |     1     |  0   |
| 연속 점수 순위 (벡터 · BM25)           |     2     |  0   |
| 임의 상수 보정 (윈도 부스팅 · 가중치)  |     2     |  0   |
| 순위 융합 · 외부 재순위 (RRF · 리랭커) |     2     |  0   |

남은 비결정 지점은 진입 판단(analyze) 한 곳이며, 이는 구 시스템에도 있었다. 같은 개념으로 진입하면 이후 순회는 순수 함수라 결과가 같고, 갈렸다면 어디서 갈렸는지 개념 목록으로 특정할 수 있다.

사용자가 체감하는 답변 변동은 여전히 남아 있다(§10 한계 4).

바뀐 뒤에 얻은 것은 정확도 향상이 아니라 **검증 가능성**이다. "원문이 그은 참조 중 그래프가 빠뜨린 것이 없다"(§4 census)는 유사도 검색에서는 쓸 수 없는 문장이다.

### 검색 단계가 0인데 왜 답이 흔들리나

"0단계"는 매번 같은 답이 나온다는 뜻이 아니라, **같은 개념으로 진입하면 결과가 같다**는 뜻이다. 흔들림은 검색 구간이 아니라 그 앞에 있다.

첫 화면에서 같은 질문을 세 번 넣으면 회수 문단이 세 번 다 달랐다. 히스토리가 비어 있어 입력은 매번 동일했으므로, 원인은 입력이 아니다.

원인은 진입 판단에 **정답이 여럿인 선택**을 시킨 데 있다. 프롬프트는 35개 토픽 목록에서 "최대 3개"를 고르게 하는데, 위 질문은 수행의무 식별·기간에 걸쳐 vs 한 시점 인식·진행률 측정이 모두 정당한 쟁점이다.

고를 개수도, 무엇을 고를지도 입력만으로 정해지지 않는다.

후보들이 근소하게 갈리는 상태에서는 추론 과정의 미세한 수치 차이가 순위를 뒤집는다. 노이즈가 원인이 아니라 증폭기이며, 후보가 확실히 갈리는 질문에서는 같은 답이 나온다.

- **temperature와 seed로는 잡히지 않는다** — 둘 다 설정했으나 위 3회 실측은 그 상태에서 나온 결과다
- **이산 진입이 차이를 증폭한다** — 주제 힌트가 하나만 바뀌어도 사례·적용지침의 수집 범위와 하위 개념 확장이 통째로 갈린다
- **결정적 경로는 이미 있다** — 용어사전 매칭은 질문 문자열만으로 동작한다. 진입을 얼마나 이 경로에 맡길 수 있는지는 아직 측정하지 않았다

같은 뿌리에서 나온 결함 하나는 수정했다. 하위 개념 확장이 집합을 순회해 프로세스마다 문단 우선순위가 달라지던 문제로, 기준서 목차 순서를 따르는 리스트로 바꿨다.

세 번째는 결정론 구조의 대가다. 흔들리는 지점을 하나로 줄인 대신, 그 하나가 흔들렸을 때의 진폭은 오히려 커졌다.

유사도 검색이라면 미세한 질의 변화가 순위의 미세한 변화로 남는다. 이산 분기에서는 계단식으로 커진다.

얻은 것은 원인 특정이다. 두 실행이 갈렸을 때 진입 개념 목록만 비교하면 어디서 갈렸는지 드러난다.

다만 흔들림의 크기 자체는 아직 측정하지 않았다.

### 최신 GraphRAG 기법을 붙이지 않은 이유

한계 5·6의 해법 후보로 검토했으나, 아래 셋은 이 프로젝트의 전제와 충돌해 보류했다.

- **커뮤니티 탐지(Leiden)** — 위계가 없는 LLM 추출 그래프에서 위계를 만들어내는 절차다. 이 그래프는 목차 위계 79간선이 원문에 이미 저작돼 있어 재발견할 대상이 없다
  - 다만 목차를 가로지르는 상호참조 264간선에 한정하면 새 군집이 나올 여지는 있다
- **커뮤니티 사전 요약** — 요약문은 LLM 생성물이라 근거 경로에 AI 창작을 다시 들인다. "뼈대는 AI 생성물이 아니다"라는 §8의 전제와 정면으로 충돌한다
  - 붙인다면 인용 대상에서 제외한 탐색 전용 레이어여야 한다
- **상위 노드 자동 집계** — 클러스터링으로 상위 요약 노드를 만드는 기법인데, 이 그래프의 상위 노드(개념 80)는 원문 목차로 이미 저작돼 있다

반대로 이중 레벨 진입(주제 힌트라는 고수준 축 + 용어사전이라는 저수준 축)은 별도로 붙일 것 없이 §3에 이미 구현돼 있다.
